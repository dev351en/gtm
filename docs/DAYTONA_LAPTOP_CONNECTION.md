# Connect your laptop to the existing Daytona game

Double-click **`Start-Daytona.bat`** (or `connect_daytona_server.bat`) in the extracted repository. This connects to your existing sandbox `b6a826ca-4dac-4716-b7b9-236b88b4718e`. It needs Python 3.10 or newer, Windows OpenSSH Client, and your existing `DAYTONA_API_KEY` in the environment or the repository's private `.secrets.env`. An existing `.venv` is used automatically. No Python packages or paid tunnel service are needed. Keep `.secrets.env` private; do not upload it to GitHub. `DAYTONA_SANDBOX_ID` is optional and overrides the default only when you deliberately set it.

The window says **READY only after OpenSSH confirms that forwarding setup completed and the actual Minecraft server answers both a status request and a matching ping through that tunnel**. Open your matching Minecraft Java Edition client and connect to **`127.0.0.1:25565`**. Keep the window open while playing; Ctrl+C disconnects this laptop. The connector closes only its own SSH process and revokes only its own short-lived token. It never stops unrelated tunnels. An occupied local port, stopped sandbox, failed host-key check, or nonresponding game produces an error instead of a false ready message. If another local game wins the port while SSH connects, it cannot satisfy readiness. A running server with `enable-status=false` must have status checks deliberately enabled by its owner before this connector can verify readiness.

OpenSSH saves the gateway host key on the first connection (`accept-new`) and rejects a changed key. Verify any key-change warning through Daytona before changing `known_hosts`. The connector uses the documented `app.daytona.io` v0 API and `ssh.app.daytona.io` gateway, refuses HTTP redirects, and does not print credentials or raw SSH/API errors. `Start-Daytona.bat --check` checks only local prerequisites and makes no network calls.

**Connecting and deploying are separate actions:** this launcher does not install the GitHub update on Daytona, start a stopped sandbox, restart Paper, replace a world, or change saved accounts. The existing cloud server must already contain the intended update and be running. The portable **`Start-GTM-Java-Only.bat`** launcher starts the separate local laptop copy; do not run both on port 25565. A successful connection check establishes connectivity, not that every new asset has been deployed.

The connector passed **39 offline tests** for credential handling, request scope, status parsing, failed readiness, local-port races, and owned-process cleanup. Reproduce with `python -m unittest discover -s tools -p test_daytona_tunnel.py -v`. The tests use synthetic responses and processes, without real credentials or network connections. **Native Windows execution and connection to the live Daytona server remain unverified.** Official API reference checked on 25 November 2026: [Daytona SSH access](https://www.daytona.io/docs/en/ssh-access/) and [Daytona API](https://www.daytona.io/docs/en/tools/api/).

The readiness observer privately consumes bounded OpenSSH diagnostics and never displays them, because they can include the session token. It requires the listener-attempt line followed by entry into the client session; the listener-attempt line alone is emitted before `bind()` and is insufficient. This ordering and the `ExitOnForwardFailure` behavior were checked against upstream [OpenSSH 7.7 forwarding setup](https://github.com/openssh/openssh-portable/blob/V_7_7_P1/ssh.c), [7.7 session loop](https://github.com/openssh/openssh-portable/blob/V_7_7_P1/clientloop.c), [10.2 forwarding setup](https://github.com/openssh/openssh-portable/blob/V_10_2_P1/ssh.c), and [10.2 session loop](https://github.com/openssh/openssh-portable/blob/V_10_2_P1/clientloop.c). An unrecognized diagnostic format fails readiness instead of guessing success.
