# Pinned dependency telemetry, optional discovery and interrupted tests

## Finding and supported setting

The installed Floodgate build has an independent bStats setting. Disabling the global `plugins/bStats/config.yml` does not disable this particular reporter. The supported setting is the nested `metrics.enabled: false` in `plugins/floodgate/config.yml`; it preserves the existing UUID, key and authentication configuration.

The offline investigation inspected the exact installed JARs and their packaged configuration, without starting a plugin, contacting an endpoint, retrying a rejected request or modifying a dependency binary. The [machine-readable audit](reports/DEPENDENCY_TELEMETRY_R4.json) contains artifact hashes, sanitized configuration observations and the limits of the finding. The [pinned bytecode excerpts](reports/PINNED_DEPENDENCY_TELEMETRY_BYTECODE_R4.txt) retain the relevant configuration and scheduling branches.

| Pinned dependency | Supported opt-out inspected | What the code does |
|---|---|---|
| Floodgate 2.2.5-b141 | `plugins/floodgate/config.yml`: nested `metrics.enabled: false` | Reads `FloodgateConfig.getMetrics().isEnabled()` and passes that boolean directly to its relocated `MetricsBase` constructor. False skips scheduling. |
| Geyser Spigot 2.12.1-b1308 | `plugins/bStats/config.yml`: `enabled: false` | Its Spigot metrics adapter resolves the plugin-directory parent and the shared bStats configuration. |
| VaultUnlocked 2.20.3, bStats | `plugins/bStats/config.yml`: `enabled: false` | Its Bukkit bStats adapter reads the shared enable flag. |
| VaultUnlocked 2.20.3, FastStats | `plugins/faststats/config.properties`: `enabled=false` | Submission requires both the configuration enable flag and the supported `faststats.enabled` JVM property. The property can also be explicitly false. |
| ViaProxy 3.4.14 | Existing `-DskipUpdateCheck=true` retained | The exact fat JAR contains no nested JAR and no bStats/FastStats identifiers in its class, YAML or properties entries. That scan does not claim that the proxy has no other network functions. |

The exact Floodgate SHA-256 is `21570aff9ce17d6983928e8552777760e1ede5050026b04c686b0ae112e6fd7e`. Its embedded resource is the root JAR entry `config.yml`, which defaults this independent switch to true. The `org.geysermc.floodgate.util.Metrics` constructor reads the metrics configuration at offsets 4–8, reads `isEnabled()` at offset 27 and passes the boolean at offset 74. In `org.geysermc.floodgate.shadow.org.bstats.MetricsBase`, constructor offsets 121–123 branch directly to the return at 130 when the flag is false; only the true branch calls `startSubmitting()` at 127.

The similarly named `bstats.relocatecheck` property controls relocation validation. It is not a telemetry opt-out. No `bstats.enabled` property was found in this pinned class, so the repair uses the actual configuration flag rather than an assumed JVM option.

At investigation time, global bStats and FastStats were already false, while Floodgate's independent switch was true in the interrupted functional and ordinary paid-profile copies. The preserved original remains unchanged. The three working copies were subsequently observed with all three switches disabled. These are checks of configuration bytes and scheduling code; they are not a universal certification that every dependency can never make an outgoing request. The audit also does not have a rejected-request caller stack trace: it identifies the concrete remaining enabled reporter path.

## Separate embedded ViaVersion update check

A subsequent clean startup, run `20261125T022947312642Z`, was interrupted before gameplay by a second automatic-review rejection, this time of the embedded ViaVersion optional update request. The same pinned ViaProxy JAR contains this updater even though it does not contain the bStats/FastStats implementations. The existing ViaProxy `skipUpdateCheck` property governs ViaProxy's own update task and does not govern ViaVersion's separate check.

The actual wrapper changes directory to `integration-probe-r4/proxy`, or `proxy-profile` for the ordinary local account. `ViaProxyViaVersionPlatform` passes that current directory to `UserConnectionViaVersionPlatform`; the latter loads `viaversion.yml` there. The directory was correct. The pinned embedded configuration implementation itself prevents the expected YAML switch from taking effect: `AbstractViaConfig.getUnsupportedOptions()` marks `check-for-updates` unsupported, `Config.loadConfig()` removes it, and `loadFields()` reads the now-absent option with a default of true. Both observed YAML files contain the update-check comment but no effective update key. Repeatedly rewriting that key would not establish an opt-out.

The public configuration API exposes `ViaVersionConfig.setCheckForUpdates(false)`. The pinned lifecycle supplies a sufficiently early hook: a supplier registered through `ProtocolTranslatorInitEvent.registerPlatform` runs during the manager's enable listeners, after configuration reload and before `onServerLoaded()` checks the update flag. The isolated harness now uses that supported API and requires the getter to read back false. The later `ViaLoadingEvent` occurs after the updater check and is too late.

The scratch adapter delegates the original public launcher-agent entry and original `ViaProxy.main`, preserving its existing instrumentation/classloader path. It does not replace third-party classes or modify the pinned binary, endpoints, authentication or protocol behavior. Before startup, it verifies event registration and the unchanged pinned dependency. A failed required check stops the isolated startup process. The cohort also checks the built adapter's source/JAR/manifest evidence before any child or pack listener and waits for the actual early-setting marker before starting Paper. A second public lifecycle check runs before proxy bind. Unreviewed external proxy plugins are refused because they could alter the inspected lifecycle.

Nine offline Java assertions verified the real pinned configuration setter, repeated application, public event delivery, failed-setting refusal and original agent delegation. Seven Python preflight cases verified missing/changed inputs, source changes, missing agent proof and forbidden third-party class replacement. The adapter's `--verify-only` branch returns before original proxy startup; these checks started no server or network listener. The adapter SHA-256 is `d19624dafaf2c3ee4720a65c996df31d434417287db42ac54513b0379172f3cc`. Its source-checkout-only documentation is `integration-probe-r4/viaproxy-optout/README.md`. Actual later startup evidence remains distinct from these offline checks.

## Third interruption: optional official discovery warmup

Standard run `20261125T023919335912Z` was separately blocked by automatic approval review during the scratch metadata warmup, before Paper started or any gameplay check ran. The parent observed no Paper log or seasonal report. This run therefore has **zero gameplay acceptance records**; it is not a failed seasonal mechanic, a continuation of the earlier 80-check fixture, or a completed pass. The rejected run is not polled or retried.

The offline source audit read `integration-probe-r4/WarmPaperMain.java`. That helper contains two fixed ordinary HTTPS metadata GETs: Minecraft's client-discovery path for `MinecraftPE/builds/1.0.0.0` and the franchise authorization service's `/.well-known/openid-configuration`. It sets `Accept: application/json`, supplies no request body or authorization/cookie header itself, consumes the response into a null output stream, and does not substitute a response or change signature validation. These observations describe the source; they do not establish that either blocked request completed.

The helper gives each connection a 20-second connection/read timeout, waits at most 25 seconds for the initial parallel pair, and schedules further fixed-address attempts with a scheduler shutdown scheduled 45 seconds later. After scheduling that shutdown, it delegates immediately to the original Paperclip main; an already running request can still reach its timeout. That warmup is unnecessary for the Java gameplay scenarios, so the materially different test path omits the helper entirely. There is no endpoint substitution, TLS bypass, authentication change or authorization workaround.

The packaged launcher source inspected at this point handled `--java-only` by adding `-DgeyserUdpPort=-1`. Its Paper child still loaded the ordinary plugin directory; the launcher did not exclude optional Geyser/Floodgate bootstrap code. That port setting alone is not evidence that optional bridge initialization or discovery can never run. The new scratch-only Java acceptance mode therefore requires ordinary exclusion of those optional bridge JARs and direct Paper startup, while preserving the exact core, world/account data, permissions, feature configuration and gameplay rules. Its implementation and later actual results are recorded separately. This audit does not claim that the packaged launcher already implements that stricter exclusion.
